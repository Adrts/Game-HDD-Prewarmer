# Game HDD Prewarmer 设计文档

版本：0.1（原型）
平台：Windows 10/11 x64，Python 3.10+
定位：机械硬盘游戏的**冷启动暖机加速器**（非全局缓存管理器）

---

## 1. 要解决的问题

### 1.1 现象

- 同一款游戏装在 SSD 与 HDD 上，体感差距非常大。
- HDD 上游戏读取吞吐长期只有个位数 MB/s，资源监视器显示磁盘 **IO 活动时间 100%**。
- 读写队列里全是零碎请求。
- 冷启动第一次进主菜单、第一次进场景、第一次开界面时卡顿最明显。

### 1.2 根因

不是"大文件顺序读得慢"，而是**大量随机小块 IO 把机械硬盘的 IOPS 打满**。

- 100% 活动时间 + 个位数 MB/s 吞吐 ⇒ 平均单次传输只有约 32–64 KB，寻道和旋转延迟占了绝大部分时间。
- SSD 的 4K 随机 IOPS 是数万级，所以同一游戏在两种盘上差距被放大。

### 1.3 工具要解决的那个子问题

系统在游戏运行中其实已经把资源读进过内存（备用内存涨到 20 GB），但这些缓存是"玩过之后"才有的。冷启动时页面还没建立，玩家只能靠"到处逛地图、反复开窗口"手动把资源提前触发一遍。

**本工具做的事：在游戏启动前，人工造出"第二次运行才有的缓存状态"。**

### 1.4 边界（明确不做的事）

- 不修改游戏文件、不改变路径、不替换资源、不注入进程、不驱动介入。
- 不锁定页面缓存；内存紧张时系统仍可回收，效果是概率性的。
- 不保证消除所有卡顿；解压、反序列化、GPU 上传、着色器编译不在覆盖范围内。

## 2. 设计思路

### 2.1 原理

进程读取文件的页会进入 Windows 系统页面缓存，缓存属于内核全局，按"卷 + 文件 + 文件内偏移"索引，与进程生命周期无关。预热进程读完退出后页面依然保留在 Standby（备用）列表中；游戏之后读取同一文件同一区间时直接命中内存，不再产生机械盘寻道。

页面进入 Standby 后按近似 LRU/时钟算法回收，**越晚读入的页面越靠后，越不容易先被回收**。因此"读完立刻启动游戏"有实际意义。

### 2.2 三个关键设计决策

#### 决策一：按物理扇区顺序（LCN）预热

传统做法是按目录遍历顺序读，这会让磁头在盘片上来回横跳，预热阶段自己就把寻道开销吃满了。

本工具通过 `FSCTL_GET_RETRIEVAL_POINTERS` 查询每个文件在卷上的**起始 LCN（逻辑簇号）**，按 LCN 升序排序后依次读取。LCN 与物理位置单调对应，等价于"从盘片外圈往里圈顺着读一遍"，磁头基本单向移动，把总寻道距离压到接近顺序读的水平。

> 取第一个非稀疏 extent 的 LCN 作为排序键。碎片化文件在文件内部仍会产生少量寻道，但文件级顺序正确后，跨文件的磁头往返基本消除。

#### 决策二：超出预算时，从尾部截断

用户给定"允许占用的缓存总量"。候选文件按 LCN 排序后从头累加，累加到再加一个就超预算时立即停止，尾部全部丢弃。

这样做的收益：

1. 读入的区间在物理上是**连续的一段**，读取过程最接近顺序读；
2. 不会出现"读到一半发现预算不够"的浪费；
3. 结果可预测、可复现，便于和未预热做对照。

#### 决策三：只读不处理，数据读出来即丢弃

工具只负责"让文件页进入系统缓存"，不解析、不保存、不解压、不建索引。读取使用 1 MB 复用缓冲区，数据读到缓冲区后立刻被下一次读取覆盖，不产生额外内存分配和驻留。

由此带来一个必要约束：**读取顺序即缓存新鲜度顺序**。LCN 靠后的文件最后被读入，进入 Standby 最晚，最不容易被率先回收。

### 2.3 为什么不并发、不限速

- 并发读取会把 HDD 的请求队列塞满，磁头在多个文件之间反复抖动，总吞吐反而下降。原型采用严格串行：一个文件读完再开下一个。
- 不额外限速：排序后的读取已经接近顺序读，对系统干扰远小于随机读；且预热耗时直接决定"读完到启动游戏"的时间窗口，人为限速不划算。若实测发现系统卡顿，后续可加入吞吐上限。

### 2.4 打开方式

`CreateFileW` + `GENERIC_READ`，共享标志 `FILE_SHARE_READ | WRITE | DELETE`（不阻塞游戏或启动器）。

**不使用 `FILE_FLAG_SEQUENTIAL_SCAN`**：该标志告诉缓存管理器"这份数据读完就不再需要"，其预读/回收启发式与本工具"读完后要长期留在缓存里"的目标相反。

## 3. 工作流程

```text
① 用户选择游戏安装目录
│
▼
② 用户设置两个参数
   总缓存上限（GB）
   单文件体积上限（MB）—— 只预热小于该值的文件
│
▼
③ 递归遍历目录，收集文件清单
   跳过符号链接/联接点、跳过无法访问的目录
   按体积过滤，得到候选集合
│
▼
④ 显示候选统计：文件数 + 总体积
│
▼
⑤ 逐文件查询起始 LCN（FSCTL_GET_RETRIEVAL_POINTERS）
   查询失败（非 NTFS / 加密 / 被独占锁定）的记为空，排到末尾
│
▼
⑥ 按 LCN 升序排序 → 从头部累加 → 超预算处截断
│
▼
⑦ 用户确认预热计划（数量 / 体积 / 是否发生截断）
│
▼
⑧ 严格串行读取：CreateFileW → ReadFile(1 MB) 循环 → CloseHandle
   数据不处理、不保存，只为建立页面缓存
│
▼
⑨ 提示用户尽快启动游戏本体
   越早启动，预热页在 LRU 中越新，越不容易被回收
```

## 4. 代码结构（单文件）

```text
Game-HDD-Prewarmer/
├─ main.py                 单文件程序，按注释分为五段：
│                            一、Windows 原生调用（打开/读取文件、查询 LCN）
│                            二、扫描（遍历、体积过滤、LCN 采集、排序与截断）
│                            三、预热读取（串行循环与统计）
│                            四、图形界面（tkinter）
│                            五、入口
└─ docs/design.md          本文档
```

### 4.1 Windows 原生调用层

| 接口 | 说明 |
| --- | --- |
| `first_lcn(path) -> int \| None` | 打开文件，用 `FSCTL_GET_RETRIEVAL_POINTERS` 取首个非稀疏 extent 的 LCN |
| `read_all_discard(path, buf) -> int` | 打开文件，循环 `ReadFile` 直到读完，返回读到的字节数 |

关键常量与结构：

```text
FSCTL_GET_RETRIEVAL_POINTERS = 0x00090073
输入：STARTING_VCN_INPUT_BUFFER { LARGE_INTEGER StartingVcn = 0 }
输出：RETRIEVAL_POINTERS_BUFFER {
         DWORD ExtentCount;
         LARGE_INTEGER StartingVcn;
         struct { LARGE_INTEGER NextVcn; LARGE_INTEGER Lcn; } Extents[];
      }
Lcn == -1 表示稀疏区间；ExtentCount == 0 表示数据驻留在 MFT（常驻小文件）
```

- 查询失败一律返回 `None`，不中断流程。
- LCN 为卷内偏移，跨卷目录无法统一排序；原型假定游戏目录位于同一卷。

### 4.2 扫描与计划

```text
Candidate(path, size, lcn, file_id)
ScanStats(files_seen, matched_files, matched_bytes,
          skipped_by_size, lcn_missing, elapsed)
```

- 遍历使用 `os.scandir` 手写栈式递归：跳过 `is_symlink()` 条目，维护 realpath 已访问集合防止联接点成环。
- 过滤条件：`0 < size <= 单文件上限`。
- 排序键：`(0, lcn)` 在前，`(1, file_id)` 在后；`file_id` 取自 `st_ino`（NTFS 文件索引 ≈ MFT 记录号），作为无 LCN 时的兜底顺序。
- 截断：按排序结果累加，**在第一个放不下的文件处停止**，不跳过、不继续。

### 4.3 预热读取

```text
WarmStats(files_done, files_failed, bytes_read, elapsed, avg_mbps)
```

- 复用单个 1 MB `ctypes` 缓冲区，减少分配与常驻内存。
- 每次 `ReadFile` 的返回长度不做任何校验或处理，直接进入下一轮。
- 单文件失败（被锁、被删、权限不足）记录后继续下一个，不中断整批。

### 4.4 图形界面

- 单窗口单按钮流程：`开始 → 扫描 → 弹窗确认 → 预热 → 完成提示`。
- 扫描与预热都在后台线程执行，UI 线程通过队列（`queue.Queue` + `after` 轮询）接收进度，避免界面假死。
- 关闭窗口即退出进程，不阻塞系统。

## 5. 参数与默认值

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| 总缓存上限 | 10 GB | 44 GB 内存 + 16–17 GB 游戏工作集的场景下，留足启动期分配空间 |
| 单文件上限 | 4 MB | 只预热小文件，避免把大体积视频/音频包读进来 |
| 读取缓冲区 | 1 MB | 与 HDD 顺序读的收益拐点对应 |
| 并发度 | 1 | 严格串行 |
| 限速 | 无 | 见 2.3 |

预算建议：`预热总量 ≤ 总内存 − 系统/后台占用 − 游戏工作集 − 3~5 GB 安全余量`。预热过量会导致游戏启动分配内存时把刚建立的 Standby 大量回收，预热白做。

## 6. 已知限制

1. **概率性**：页面无法锁定，内存压力大时仍会被回收。
2. **大包盲区**：现代游戏资源大量封装在 `.pak` / `.bundle` / `.pck` 等单文件大包内，"按文件体积过滤"会把这些大包整体排除，而实际的随机小 IO 恰恰发生在包内部。这是本原型最大的命中率损失来源。
3. **无访问轨迹**：原型不采集游戏实际读了什么，只按体积和物理位置启发式挑选。
4. **碎片化文件**：排序只保证文件间的物理顺序，文件内部碎片仍会产生寻道。
5. **非 NTFS / 加密 / 跨卷**：LCN 不可得时退化为按 MFT 记录号排序。

## 7. 验证方法

**三组对照**

| 组 | 条件 | 预期 |
| --- | --- | --- |
| A | 冷启动，不预热 | 基线，记录到主菜单/首次进场景耗时与卡顿次数 |
| B | 冷启动，预热后立即启动 | 应明显优于 A |
| C | 第二次启动（系统自然缓存） | B ≈ C 说明预热生效；C 也慢说明瓶颈不在页面缓存 |

**辅助手段**

- RAMMap 查看 Standby 中的文件页占用与分布。
- 资源监视器观察预热后游戏启动阶段的 IO 活动时间、平均延迟、队列长度是否下降。
- 双遍自检：预热完成后立刻把同一批文件再读一遍，若第二遍达到内存速度（> 1 GB/s），说明页面仍在缓存中；若没有，说明已被回收，应下调预热总量。

## 8. 后续演进

1. **轨迹驱动**：解析 `C:\Windows\Prefetch\*.pf` 或 ETW `Microsoft-Windows-Kernel-File`，拿到游戏启动阶段的真实文件清单，用它替代体积启发式。
2. **区间预热**：按 `(文件, 偏移, 长度)` 预热大包内部的热点区间，而不是整个文件。
3. **逆序回放**：按轨迹逆序读取，让游戏最先访问的文件进入 Standby 最晚、最抗回收。
4. **物理布局精排**：用完整 extent 列表按 LCN 合并读取计划，跨文件消除内部碎片。
